# Desktop Release Qualification & Checklist

Releases fall into two tiers. Most releases are Tier 1 and need only automated checks; the manual hardware and model procedures in the rest of this document apply only to Tier 2.

### Tier 1 — Routine Releases (Patch & Minor Updates)

Changes to app code, UI, backend APIs, or docs that do not alter `desktop/locks/processing-*.json` or `desktop/models.json` carry forward existing hardware/model qualification. They require only:

- a clean git revision;
- passing automated CI (`pytest`, `vitest`, neutrality/SPDX);
- built/signed installers with SHA-256 checksums;
- passing automated smoke tests (`native-smoke.py` / `packaged-smoke.mjs`).

### Tier 2 — Full Hardware & Model Qualification (New Targets / Lock Changes)

The physical platform matrix, 20-song evaluation corpus, SmartScreen/Gatekeeper prompt observations, and 4-hour physical show procedures in the rest of this file apply only when introducing a new OS/arch target, changing runtime/model locks, or running an explicitly requested hardware qualification campaign.

A Tier 2 result applies to the runtime/model locks and artifact SHA-256 it was recorded against, and carries forward to later app commits until those locks change. Automated source tests and virtual displays verify plumbing, but physical audio output, external display behavior, and clean-machine installation must be verified on real hardware. Use `desktop/qualification/matrix.template.json` as the machine-readable record, paired with the hardware inventory generated by `desktop/qualification/qualify.py` and each artifact's immutable `.shapp.receipt.json`.

## 1. Tier 2 Qualification Checklist

- [ ] **Candidate Identity:** Candidate version and exact clean source revision recorded.
- [ ] **Immutable Inventory:** Every installer, portable `.shapp` payload, runtime pack, receipt, and checksum is tied to the same candidate inventory.
- [ ] **Reproducibility Check:** Two clean builds compared; any platform-container nondeterminism is documented without weakening modeled payload verification.
- [ ] **License & Notice Delivery:** Installer contents include the source/license inventory, `native/notices/`, and all bundled font licenses.
- [ ] **Platform Matrix Results:** Explicit results recorded for Windows 11 25H2 x86-64, macOS 14+ Apple Silicon, Ubuntu 24.04 x86-64, Ubuntu 24.04 ARM64, and the target Asahi Linux show system.
- [ ] **Signing & OS Prompts:** Exact per-artifact signing status and observed SmartScreen/Gatekeeper behavior recorded in the release notes; no instructions tell users to disable OS security globally.
- [ ] **Lifecycle & Recovery:** Prepared-media clean install, offline restart, update, interrupted update, recovery, uninstall data retention, and reinstall pass on every target.
- [ ] **20-Song Processing Evaluation:** Every advertised processing route passes the fixed 20-song quality, timing, stem, memory, speed, interruption, and offline checks.
- [ ] **Linux AppImage Outer-Image Verification:** AppImage anchor creation, rotation, launch, and standalone recovery pass substitution tests (or update/recovery remains explicitly fail-closed for AppImage).
- [ ] **4-Hour Physical Show Test:** Continuous 4-hour 1080p physical audio/projector show passes on every target, including the ARM64 show machine.
- [ ] **Public Tree Hygiene:** Public files contain no internal planning names, private service addresses, credentials, evaluation corpus files, or assistant attribution trailers.
- [ ] **Support Diagnostics:** `docs/support-diagnostics.md` verified for secret/media scrubbing.
- [ ] **Release Notes Completeness:** Release notes list exact source revision, artifact filenames/SHA-256s, qualified platform/model/device rows, known failures, and any `untested` rows.
- [ ] **Publication Sign-Off:** Repository visibility, release publication, code-signing enrollment, and paid cloud resources each have explicit maintainer authorization.

## 2. Platform Matrix & Clean-Profile Lifecycle

Target platforms: **Windows 11 25H2 (x64)**, **macOS 14+ (Apple Silicon)**, **Ubuntu 24.04 (x64)**, **Ubuntu 24.04 (ARM64)**, and the **Asahi Linux show system**.

For each target, start from a clean machine or user profile with no developer caches, system Python dependencies, existing Singhouse data, runtime packs, or models:

1. Record OS build, CPU, RAM, GPU/driver, display topology, audio device, filesystem, desktop/session type, kernel, and free disk space.
2. Verify the downloaded installer's SHA-256 and record the exact OS security prompt on first launch.
3. Exercise and record distinct results for: clean install, first launch, second-instance refusal (`owner.lock`), normal restart, offline restart, signed slot upgrade, interrupted upgrade + rollback recovery, uninstall with user data retained, reinstall, and manual data removal.

---

## 3. End-to-End Processing Evaluation (20-Song Corpus)

Evaluate every advertised model/device route against the private 20-song evaluation corpus (covering repetition, duets, quiet vocals, dense mixes, and long tracks; never commit corpus media or lyrics to the repo):

1. **Separation:** Import audio and complete Pass 1 (Demucs) and Pass 2 (RoFormer). Verify all expected stems are readable, aligned, non-silent, and un-truncated; compare audibly against reference stems.
2. **Transcription & Alignment:** Run Heart transcription and alignment. Compare corpus Word Error Rate (WER) and p95 word-start timing against the reference baseline:
   * Candidate WER may regress by **at most 2 percentage points**.
   * Candidate p95 word-start timing may regress by **at most 100 ms**.
   * Inspect any new whole-section omission individually.
3. **Editor & Playback:** Edit lyrics and word timings, save, restart, queue, play, seek, pause/resume, and complete playback.
4. **Resource Envelope:** Record wall-clock duration and peak RAM/VRAM. Derive minimum hardware recommendations as **measured peak + 25% headroom**, and verify on representative hardware.
5. **Offline Execution:** Disable networking, restart, and run local inference using the already-installed runtime and model cache.

---

## 4. Controlled Failure & Recovery Tests

Inject interruptions during: runtime/model download, runtime activation, Pass 1 and Pass 2 separation, update payload download, slot extraction, SQLite backup, slot selection, first target startup, and pre-frame renderer crash. Also trigger a bounded insufficient-memory refusal.

Verify after every injected failure:

* Prepared-media playback and the last working application remain usable.
* Failed ingest jobs remain retryable without leaving partial files marked as complete.
* Prior verified runtime/model selections remain active when a replacement fails.
* Application and SQLite rollback belong to the exact same signed update pair, and replayed/same-sequence update metadata is rejected.

---

## 5. Four-Hour Physical Show Test

Run a continuous **4-hour 1080p show** on physical hardware for every launch target (using prepared media):

* Exercise host window minimize/restore, switching the host to an inactive workspace for ≥ 15s while keeping the projector visible, projector close/reopen, fullscreen toggle, physical display disconnect/reconnect, audio output switching, physical audio disconnect/reconnect, seek, pause/resume, and track transitions.
* Record application logs and wall-clock timestamps for any audio dropout, frozen projector frame, or catch-up jump.
